# Architecture

How Rook is put together, and why each boundary is where it is. Decisions that
are expensive to reverse have their own record in [adr/](adr/).

---

## The shape of it

```text
┌─────────────────┐
│  Tauri desktop  │  React 19 + Vite. Tauri APIs isolated in one adapter, so a
│     client      │  web client needs no other change.
└────────┬────────┘
         │ HTTP (sends, reads, uploads)        WebSocket (receives)
         │                                      │
┌────────▼────────┐                    ┌────────▼────────┐
│   apps/api      │                    │ apps/realtime   │
│                 │                    │                 │
│ auth            │                    │ socket gateway  │
│ communities     │                    │ outbox relay    │
│ messages        │                    │ presence        │
│ media authz     │                    │                 │
└────┬───────┬────┘                    └────┬──────┬─────┘
     │       │                              │      │
     │       └──────────┐      ┌─────────────┘      │
     │                  │      │                    │
┌────▼─────┐      ┌─────▼──────▼───┐        ┌───────▼────────┐
│PostgreSQL│      │     Redis      │        │ Object storage │
│          │      │                │        │  (S3-compat)   │
│ source   │      │ cache, queue,  │        │                │
│ of truth │      │ rate limits,   │        │ file bytes     │
│          │      │ fan-out        │        │                │
└────▲─────┘      └───────▲────────┘        └───────▲────────┘
     │                    │                         │
     └────────────┬───────┴─────────────────────────┘
                  │
         ┌────────▼─────────────┐
         │ services/media-worker│  Sharp processing, scheduled housekeeping
         └──────────────────────┘
```

The division of labour that matters most: **the client sends over HTTP and
receives over WebSocket.** Sends need persistence, validation, precise errors
and idempotent retries — all of which HTTP status codes express well. The
socket exists to push changes outward. Sending over the socket would mean
reinventing request/response semantics inside a protocol that has none.

## Package boundaries

Dependencies point one way: apps depend on packages, packages depend on
packages closer to the domain, and nothing depends on an app.

```text
contracts ◄── everything (schemas; one dependency, zod)
   ▲
config ◄── observability ◄── database ◄── messaging ◄── apps
   ▲                            ▲            ▲
   └──────── auth ──────────────┘            │
   └──────── media ───────────────────────────┘
   └──────── queue ───────────────────────────┘
```

Two of these boundaries are load-bearing:

**`@rook/contracts` has exactly one runtime dependency (Zod) and imports
nothing from the workspace.** That is what makes it safe for the desktop client
to depend on: pulling in contracts can never drag a database driver,
server-side code or credentials into the frontend bundle. Every HTTP body and
every realtime event is defined there once and validated on both sides.

**`@rook/auth` has no database dependency.** Password hashing, token handling
and capability resolution are pure functions over configuration. The session
lookup is injected as a callback, so the same authenticator serves both the API
and the gateway with identical behaviour — a token one rejects cannot be
accepted by the other.

### Why the domain layer is separate from the transport

`@rook/messaging` holds the chat domain: authorisation decisions, the
persist-then-publish ordering, and result types the transport maps to status
codes. It knows nothing about HTTP. That is what lets the integration suite
drive real flows against a real database without starting a server, and it
means an alternative transport (a gRPC gateway, a CLI) would reuse the logic
rather than reimplement it.

## Data model

Eleven tables. The full schema with its reasoning is in
[`packages/database/migrations/0001_initial_schema.sql`](../packages/database/migrations/0001_initial_schema.sql),
which is written to be read.

```text
users ──┬── sessions
        ├── community_members ── communities ── channels ── messages
        │                                                      │
        └── media_assets ── media_variants                     │
                  └──────── message_attachments ───────────────┘

event_outbox   (no foreign keys: events outlive what they describe)
```

### UUIDv7 everywhere

Every id is a UUIDv7, generated by the application. Three consequences, all
deliberate:

1. **Sortable.** Lexicographic byte order equals creation order, so
   `order by id desc` on messages is chronological and needs no timestamp
   column in the index. A message id *is* a pagination cursor.
2. **Index-friendly.** Inserts land at the right edge of the B-tree instead of
   scattering across it as UUIDv4 does. For a table taking the bulk of the
   write volume, that is the difference between a compact index and constant
   page splits.
3. **Partition-ready.** The embedded timestamp means a future time-range
   partitioning scheme can be derived from the key itself.

Generating them in the application rather than the database means an id is
known *before* the insert — so it can be logged, returned to an optimistic
client, and written into the outbox event in the same transaction.

### Cursor pagination, never offset

There is no offset pagination anywhere in the API. `OFFSET 50000` makes
PostgreSQL walk and discard fifty thousand rows, and in a channel that is
receiving messages while you scroll, offsets shift under you so rows are
duplicated or skipped between pages. A cursor is a position in a stable
ordering, so neither happens:

```sql
select ... from messages m
where m.channel_id = $1 and m.id < $2   -- the cursor
order by m.id desc
limit $3
```

`(channel_id, id desc)` satisfies this with a backwards index scan that seeks
straight to the cursor. Cost tracks page size, not depth into history.

### One query per page, not one per message

A page of history resolves its authors by join and its attachments by a lateral
aggregate, in the same statement. The obvious alternative — map over the
messages and fetch each one's attachments — turns a 50-message page into 51
queries. The lateral keeps it at one regardless of page size, and being inside
a `LATERAL` rather than a top-level join means attachments cannot fan out and
duplicate message rows.

## Realtime delivery

### The transactional outbox

The problem: a service that commits a message to PostgreSQL and then publishes
to Redis has two steps that fail independently. Crash between them and the
message exists but nobody was told — connected clients stay silently out of
sync with durable state. Publish first instead, and you can broadcast a message
whose transaction then rolls back.

Rook writes the event to an `event_outbox` row **in the same transaction as the
change itself**. So:

- a committed change always has its event, and
- a rolled-back change never produces one.

A relay in the gateway then claims committed rows with
`for update skip locked`, publishes them to Redis, and marks them published.
`skip locked` is what lets several gateway instances each run a relay: they
take disjoint batches rather than contending or double-publishing.

```text
API                          PostgreSQL              Relay            Redis
 │                                │                    │                │
 ├─ BEGIN ──────────────────────► │                    │                │
 ├─ insert message ─────────────► │                    │                │
 ├─ insert outbox event ────────► │                    │                │
 ├─ COMMIT ─────────────────────► │                    │                │
 │                                │ ◄── claim batch ───┤                │
 │                                │                    ├─ publish ────► │
 │                                │ ◄── mark done ─────┤                │
```

### At-least-once, and why that is the right choice

The relay can publish and then die before committing the mark, so the event is
delivered twice. That is the deliberate trade: **losing an event is
unacceptable, seeing one twice is harmless.** Every event is idempotent by id,
and the client keys messages by id — applying `message.created` for a message
already in the store is a no-op. Exactly-once would need distributed consensus
for no practical gain.

### Gap recovery

Redis pub/sub retains nothing. An event published while a client is
disconnected is simply gone. Recovery is therefore **not** a socket replay log:
on every connect and reconnect the client refetches history over HTTP, and
because messages are keyed by id, a refetch that overlaps live events cannot
duplicate anything.

This is why there is no per-client cursor on the server, no replay buffer, and
no acknowledgement protocol. PostgreSQL is already the durable record; the
socket is a notification channel over it.

### Fan-out without a firehose

Each gateway subscribes only to the Redis channels its connected clients care
about, reference-counted so two sockets watching one channel share a
subscription:

```text
rook:events:channel:<id>      messages in a channel
rook:events:community:<id>    channel creation, member joins
rook:events:user:<id>         media processing results, across a user's devices
```

The audience is resolved once, by the service that produced the event, and
stored on the outbox row. A gateway holding ten thousand sockets therefore
never queries PostgreSQL to decide who receives something. The alternative —
one firehose channel with filtering per instance — means every instance pays to
deserialise every event in the system, which is precisely what stops you adding
instances to shed load.

### Typing indicators never touch PostgreSQL

A typing indicator is worthless seconds later, is generated several times per
sentence, and nobody minds losing one. Routing it through the outbox would mean
a durable write — and a WAL record, and index maintenance — per keystroke. So
it lives entirely in Redis: a short-TTL key plus a publish on the same channel
the relay uses, so gateways need only one delivery path. It self-expires, which
is why there is no "stopped typing" event: a client that closes mid-sentence
cannot leave a stuck indicator behind.

## The media pipeline

File bytes never pass through the API.

```text
client                    API              storage           worker
  │                        │                  │                 │
  ├─ POST /media/uploads ─►│                  │                 │
  │                        ├─ reserve row     │                 │
  │ ◄─ presigned PUT ──────┤                  │                 │
  ├─ PUT bytes ───────────────────────────────►│                 │
  ├─ POST .../confirm ────►│                  │                 │
  │                        ├─ HEAD (real size)►│                 │
  │                        ├─ range read ─────►│  (magic bytes)  │
  │                        ├─ status: uploaded │                 │
  │                        ├─ enqueue job ───────────────────────►│
  │ ◄─ asset (uploaded) ───┤                  │                 │
  │                        │                  │◄─ download ──────┤
  │                        │                  │◄─ put variants ──┤
  │                        │   status: ready + outbox event ◄────┤
  │ ◄── media.updated over the socket ─────────────────────────── │
```

Proxying bytes through Node would make the API the bottleneck and its heap the
limit on file size. The signed-URL hop means the API only ever handles
metadata.

**Confirmation is the security-critical step.** At that point the client claims
"I uploaded it", and nothing it says is trusted:

- the object must exist at the key *we* authorised (keys are derived from the
  asset id, never the filename — that is how `../../etc/passwd` becomes a
  traversal bug);
- its real size comes from storage, so understating `declaredByteSize` gains
  nothing;
- its type comes from the leading bytes via a range request, never from the
  extension or the `Content-Type` the client set. An HTML file named
  `avatar.png` is the stored-XSS case this defeats.

The worker then re-encodes every variant from decoded pixels, which drops all
metadata — EXIF on a phone photo routinely carries GPS coordinates — and
enforces pixel and dimension limits read from the header *before* any decode. A
20 KB PNG can declare 50,000 × 50,000 pixels and expand to tens of gigabytes.

Processing is idempotent: status transitions are guarded in SQL
(`where status = 'uploaded'`), variants are upserted, and variant keys derive
from the asset id, so a retry overwrites its own output rather than leaking
orphans. Failures are split into **permanent** (bad bytes — marked failed, not
retried) and **transient** (storage unreachable — retried with backoff, marked
failed only once attempts are exhausted). A job that retries a corrupt file
five times is noise that hides real failures.

## Client-side state

Three stores, split by who owns the data:

| State | Owner | Why |
| --- | --- | --- |
| Communities, channels, members | TanStack Query | Ordinary server state; refetch and cache are the right model |
| Messages | A dedicated Zustand store | Written by three paths at once |
| Selection, dialogs, drafts | Zustand | Local; must survive refetches |

Messages get their own store because they are mutated by realtime events,
optimistic sends and history pagination simultaneously, and reconciling three
write paths inside a query cache is harder than owning the collection. The
store keys messages by id in a `Map`, which is what makes applying the same
message twice a no-op — the client half of the at-least-once contract.

An optimistic send appears immediately keyed by its idempotency key, and is
replaced atomically by the server's authoritative row. If it fails it stays
visible marked failed, with retry and discard; the retry reuses the same key, so
the server resolves it to the same row instead of creating a second message.
Nothing is silently dropped and nothing retries forever on its own.

## TypeScript configuration

Strict, plus `noUncheckedIndexedAccess`, `noImplicitOverride`,
`noImplicitReturns`, `noUnusedLocals`/`Parameters`, `verbatimModuleSyntax` and
`isolatedModules`.

`exactOptionalPropertyTypes` is deliberately **off**. It distinguishes "absent"
from "present and undefined", which is occasionally useful, but at library
boundaries — Fastify option bags, AWS SDK inputs — it forces a conditional
spread around every optional field without finding bugs. The distinction that
actually matters here (clearing an avatar versus leaving it alone) is modelled
explicitly with `null` instead.

Workspace packages are **composite projects**, so one `tsc -b` builds and
type-checks the whole graph in dependency order. Node-targeted packages export
a `development` condition pointing at TypeScript source, so `tsx` runs them
directly with no build step, while production resolves built `dist` through the
same `exports` map. `@rook/ui` exports source only — Vite compiles it, so there
is no build artifact to go stale.

Ambient types are declared explicitly (`"types": ["node"]`, overridden to
`["vite/client"]` for the frontend) rather than auto-discovered. Under pnpm's
isolated layout, auto-discovery depends on which `@types` happen to be
reachable, so a package can compile only because an unrelated dependency pulled
in a reference — and then break when that dependency changes.

## Observability

Every service exposes the same three endpoints. The split between them is not
cosmetic:

- **`/health/live`** is process-local. It answers "is this broken and in need
  of a restart?" and deliberately consults no dependency. Wiring Postgres into
  liveness means a brief database blip restarts every instance at once, turning
  a degraded minute into a cold-start stampede.
- **`/health/ready`** consults dependencies, each marked critical or not.
  Losing Redis degrades the API (rate limits, typing) but does not make it
  unready; losing Redis makes the *gateway* unready, because without it the
  gateway has nothing to deliver.
- **`/metrics`** is Prometheus text. Each service builds its own registry
  rather than using the global default, so tests can assert on one and discard
  it.

The metric worth watching is `rook_outbox_backlog`: a persistent backlog is the
clearest signal that realtime delivery is falling behind durable writes.
[operations.md](operations.md) covers the rest.

Logs are structured JSON with redaction applied by path at the logger, not
trusted to each call site — one careless `log.info({ user })` is all it takes
to put a password hash in permanent storage. Presigned URLs are redacted too:
they are bearer credentials for the bucket, so a log aggregator holding them is
a privilege-escalation path.
